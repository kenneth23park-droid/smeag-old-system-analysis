## 0. 이 문서의 위치 — 요구서가 2종이라는 점부터

지금 프로젝트에는 **성격이 다른 요구서 2종**이 있고, 이번 §1~§21은 그중 두 번째다.

| | A. 관리자팀 요구서 (2026-07-27) | B. 현업 요구서 (이번, §1~§21) |
|---|---|---|
| 발신 | 기숙사·아카데믹·전산 실무 | 원장·영업·수속(에이전시 접점) |
| 관심 | 통계 축·마스터 관리·전기수도·감사로그 | **등록→인보이스→커미션→수납** 의 돈 흐름과 객실 자리 |
| 정규화 산출물 | `new-admin-requirements.md` (REQ-101~212) | **이 문서** |

**겹치는 부분**: 객실 마스터/카테고리, 캠퍼스 단일화, 인보이스 스냅샷, 감사로그, 중복 배정.
**B에만 있는 것(=신규)**: 단기 45/65/85 요율, 추가비용 2종(커미션 적용/제외), 에이전시별 다건 커미션, **판매 객실유형 ≠ 실제 객실**, **슬롯 차단(가짜 학생 제거)**, 수납·완납·환불 필드군, 관리자 대리등록, 가족/그룹, **레거시 사이트에서 신전산으로 진입**, **구·신 병행운영**.

## 3. 모듈별 설계

### 3.1 학비 계산 엔진 (§6) — 신규, 최우선

**단일 함수 하나로 못 박는다.** 화면·인보이스·문서가 전부 이 함수만 호출한다(현재처럼 화면마다 계산 금지).

```
fee(course_price_4wk, dorm_price_4wk, admission_fee, weeks)
  rate(weeks) = 1주 .45 / 2주 .65 / 3주 .85 / 4주 1.00
  tuition = round( course_price_4wk × rate(weeks) )     ← 4주 이하
  dorm    = round( dorm_price_4wk  × rate(weeks) )
  admission = admission_fee                              ← 기간 무관 전액
```

- **4주 초과(D3 미결)**: 잠정안 = `4주 블록 × 100% + 나머지 주 × rate(나머지)`.
  예 6주 = 100% + 65%. 5주 = 100% + 45%. **회신 전까지 화면에 "잠정 계산" 배지 표시.**
- 결과는 **관리자 수동 수정 가능**하되, 수정 시 `override_reason` 필수 + 원계산값을 `price_snapshot` 에 함께 보존.
- **"3주 금액 맞추기" / PRE PAY 조정 입력은 폐기.** 마이그레이션: 기존 학생의 PRE PAY 값은 읽기전용 이력으로만 남기고 신규 입력칸 제거.
- 화면 표기: `4주 840,000 × 85% = 714,000` 처럼 **적용 전/후를 나란히** (§6.2 요구).

**AC**: 3주 등록 시 입학금 100,000 + 수업료 714,000 + 기숙사 756,500 = 총액이 수기계산과 정확히 일치. 인보이스 어디에도 "맞추기"류 문구가 없다.

### 3.2 추가비용 2종 분리 (§7.3)

현재 뒤섞인 3칸(`ETC FEE` / `ETC COMMISSION` / `PRE PAY`)을 **분류 있는 명세줄(line item)** 로 교체한다.

| 필드 | 값 |
|---|---|
| `kind` | `tuition` \| `dorm` \| `admission` \| `extra_commissionable` \| `extra_excluded` |
| `label` | 고객 노출 문구 (예: "Visa Extension Fee") — **내부 용어 금지** |
| `amount`, `qty`, `memo`, `internal_only` | |

- 커미션 기준액 = `tuition + dorm + extra_commissionable` (입학금 포함 여부는 **D4/NET 정의**에 종속).
- `extra_excluded` 예시 마스터: 비자연장·이민국·현지납부·대납·정부기관·기타실비 → **드롭다운 마스터로 제공**(자유 입력 남용 방지).
- 인보이스 출력: 입학금/수업료/기숙사비/추가비용(커미션대상)/추가비용(제외) **5블록 + 총액·커미션·NET**.
- `internal_only=true` 줄은 내부확인용 인보이스에만 인쇄.

### 3.3 커미션 (§8)

**모델(D4 ③ 혼합 권장)**

```
app.commission_plan  (에이전시별 N건)
  agency_id, plan_name, method: 'rate'|'fixed_per_4wk',
  rate_pct | fixed_amount,
  조건: campus_id? course_id? nationality? guardian_class? period_from/to?
  active, valid_from, valid_to, sort
```

- 인보이스 발행 화면은 **해당 에이전시의 plan 목록만** 드롭다운으로 표시(§8.2).
- 학생 조건 매칭으로 **1건 자동 선택(추천)**, 배지로 "자동선택" 표시, 관리자가 변경 가능(§8.3).
- 정액식 계산: `fixed_amount × (weeks / 4)` — **단기 주차의 소수 처리 규칙은 D2에 포함**.
- 확정 시 `invoice.price_snapshot.commission = {plan_id, method, value, base, result}` 로 **고정**.
- 현 `COMMISSION RULES`(localStorage) 화면은 **폐기 예정**으로 표시하고, 값은 초기 plan 시드로 1회 이관.

### 3.4 객실 — 실제 배정 vs 판매 유형 (§11.3·§11.4)

**핵심 아이디어: 한 배정 레코드에 축을 두 개 둔다.**

| 축 | 컬럼 | 의미 | 쓰는 곳 |
|---|---|---|---|
| 실제 | `room_id`, `bed_no`, `room_capacity` | 물리 객실·침대 | 배치도, 점유, 청소, 통계 |
| 판매 | `sold_room_type`(1/2/3/4인실), `sold_price_basis` | 고객에게 판매한 유형 | **인보이스·가격·에이전시 문서** |

- 앵칸토: 실제 4인실 유지(과거 데이터 불변) + 판매 2인실 → **가상 "Outside 2인실" 객실 생성 불필요**.
- 판매유형이 실제 정원보다 작으면 **남는 슬롯은 자동으로 차단 후보**로 제시(§12와 연동).
- 캐피탈: `sold_room_type` 기본값 = 실제 정원 (동작 변화 없음).
- **과거 데이터 보호**: 객실 구조(정원) 변경은 이력 있는 객실에 대해 금지, 대신 신규 객실 생성 + 구객실 비활성(§16 원칙).

### 3.5 슬롯 차단 (§12) — 이미 있는 것 위에 얹는다

`app.room_blocks` + `/api/blocks`(방 전체/침대/기간/사유/작업자) **이미 동작 중**. 추가로 필요한 것만:

1. **사유 코드화**: 가족2인단독 / 가족3인단독 / 싱글유즈 / 트윈유즈 / 트리플유즈 / 시설점검 / 관리자예약 / 기타(자유입력).
2. **통계 제외 보장**: 재학생 수·교사 배정·식수 산출에서 블록은 절대 인원으로 세지 않는다 → **단일 산출원 RPC(REQ-105)** 안에서 처리.
3. **차단 이력 화면**: 설정/해제 이력 조회(작업자·사유·기간).
4. **가짜 학생 청산**: `ROOM` 계정으로 생성된 가상 학생을 목록화 → 블록 레코드로 **변환 스크립트** + 학생목록에서 제외 플래그. *(원본 삭제 금지 — 신전산 오버레이에서만 숨긴다)*
5. 판매유형 축소 시 잔여 슬롯 **자동 차단 제안**(§3.4).

### 3.6 중복 배정 방지 (§14) — 3중 방어

| 층 | 방법 |
|---|---|
| DB | `app.room_assignments` 에 **배타 제약** `EXCLUDE USING gist (room_id WITH =, bed_no WITH =, daterange(check_in, check_out, '[)') WITH &&) WHERE (active)` — 기간 겹침 저장 자체가 불가 |
| 서버 | 트랜잭션 내 `SELECT … FOR UPDATE` 로 대상 침대 잠금 후 재검증. 위반 시 23P01 → 사용자 문구 반환 |
| 화면 | 저장 직전 최신 상태 재조회(§14.1·14.4). 화면을 N분 이상 열어두면 자동 새로고침 + 배지 |

사용자 문구(요구서 그대로): **"해당 객실 또는 침대는 다른 사용자가 이미 배정했습니다. 객실 현황을 새로고침한 후 다시 선택해 주세요."**

> 방막기(`room_blocks`)도 같은 배타 제약 공간을 공유해야 한다 — **블록된 슬롯에 배정 저장 불가**.

## 6. 병행운영 (§2.2·§2.3) — 🔴 결정 D1

### 6.1 레거시 사이트 → 신전산 진입 (§2.2) · 리스크 낮음, 즉시 가능

기존 도메인의 **마이페이지 / 에이전시 로그인 후 이동 / 관리자 진입** 링크의 `href` 만 신전산 URL로 교체.
에이전시는 기존 북마크를 그대로 쓴다. 되돌리기 = 링크 원복(1분).
→ **선행 확인 필요**: 레거시 웹서버 파일 수정 권한, 세션 이관(재로그인 요구할 것인지) 2건.

### 6.2 구·신 동시 저장 (§2.3) — 3안

| 안 | 방식 | 장점 | 위험 | 판단 |
|---|---|---|---|---|
| **①동결** | 전환일부터 레거시는 **읽기 전용**. 신전산만 입력 | 데이터 1벌, 충돌 0 | 롤백 시 신규분 수기 이전 | **권장** |
| **②역동기(배치)** | 신전산 입력분을 야간 배치로 레거시에 INSERT | 롤백 여지 확보 | 하루 지연·부분 실패 처리 | 차선 |
| **③실시간 이중쓰기** | 저장 시 Supabase + MySQL 동시 | 즉시 동등 | **원본 불가침 원칙 위반**, 2PC 없음 → 한쪽만 저장되는 상태 발생, 채번 충돌(학생ID·인보이스번호), 장애 시 전부 정지 | **비권장** |

> 요구서 §2.3의 목적은 "롤백 가능성"과 "검증"이다. 그 목적은 **①+일일 대사(對査) 리포트**로 달성할 수 있다 —
> 매일 `학생수·신규등록·인보이스 건수/금액·객실 점유` 를 구·신 양쪽에서 뽑아 차이표를 자동 생성.
> 실시간 이중쓰기 없이도 "양쪽이 같은가"에 답할 수 있고, 원본은 안전하다.

**권한(§2.3 후단)**: 원장/최고관리자 = 구·신 모두 조회 / 일반 직원 = 신전산만. 레거시는 **전 직원 쓰기 차단**(①안이면 자동 충족).
