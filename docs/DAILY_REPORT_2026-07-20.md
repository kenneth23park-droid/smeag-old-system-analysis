## 2. 주요 성과 상세

### 2-1. 인보이스 중복발행 방지 — **오늘의 핵심 (운영 리스크 제거)**
**문제**: 발행 버튼을 두 번 누르거나 응답 지연 중 재클릭하면 **인보이스가 이중 발행**될 수 있었음.
**원인(용어 정리)**: 확인→기록 사이의 유휴 구간에서 두 요청이 모두 통과하는 **TOCTOU 경쟁상태**(Time-Of-Check to Time-Of-Use). 사용자 행동은 **중복 제출**, 설계 원인은 **비멱등 연산**, 결과는 **이중 발행(중복 레코드)**.

**4중 방어 구축**

| 계층 | 구현 | 막는 것 |
|---|---|---|
| ① UI | 클릭 즉시 버튼 비활성 + 스피너, 진행중 재클릭 안내 | 더블클릭·연타 |
| ② 요청 | 클릭 1회 = **멱등키 1개** | 재시도·새로고침 |
| ③ **DB** | `app.invoice_issue` **UNIQUE**(멱등키 / 대상+회차) + `app.invoice_publish` RPC | ★ **TOCTOU** (최종 방어) |
| ④ 안내 | **"이미 발행되었습니다"** 메시지박스 — 인보이스번호·발행일시·발행자 + 감사로그 | 사용자 혼선 |

**검증** — DB 3회 호출 → **실제 레코드 1건**, 2·3회차는 기존 발행건 안내 / UI 연타·완료 후 재클릭 모두 차단.
적용: Manage Cash·변경환불홀딩 등 INVOICE 버튼 + **상세폼 NEW INVOICE PUBLISH** 전부 동일 경로.
