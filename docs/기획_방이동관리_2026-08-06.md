# 신전산 방 이동 관리(Room Move) 기획서

작성일 2026-08-06 · 상태: **기획(코딩 착수 전)** · 요청서: 「SMEAG 신전산 방 이동 관리 기능 개발 요청」 §1~§21

---

## 0. 결론 먼저 (설계 3원칙)

1. **"미래 배정" 전용 테이블을 새로 만들 필요가 없다.**
   레거시 `room_reserve` 는 이미 *침대 × 날짜* 1행 구조라, 미래 날짜 행이 곧 미래 배정이다.
   현재 배정 / 미래 배정의 구분은 **저장 구조가 아니라 기준일(as-of date) 파생**으로 정의한다.
   → 요청서 §2.1/§2.2 의 "미래 배정을 등록해도 현재 배정이 사라지면 안 된다"는 자동으로 성립한다.

2. **부족한 것은 배정 데이터가 아니라 "이동이라는 사건(intent)"이다.**
   레거시 `room_move` 에는 상태(검토/예정/확정), 사유, 담당자, 예정시간, 실제 이동시각이 없다.
   → 신규 원장 `app.room_moves` 가 이 사건을 관리하고, 배정 자체는 오버레이 `app.room_assignments` 로 표현한다.

3. **원본 불가침 + 오버레이 합성.** (기존 `app.room_blocks` 와 동일한 패턴을 그대로 확장)
   레거시 MySQL / `legacy.*` 스키마는 읽기 전용. 신전산 쓰기는 전부 `app.*` 에만.
   배치도 렌더 = `legacy.room_reserve`(정본·실적) **⊕** `app.room_assignments`(미래·이동) **⊕** `app.room_blocks`(차단).
   구전산 반영은 기존 `app.change_log` → 일일 역방향 동기화 경로를 그대로 탄다.

## 1. 현재 관련 테이블과 모델 (요청서 §21 사전보고 ①)

### 1.1 레거시 원장 (읽기 전용, `legacy.*` 로 미러링됨)

| 테이블 | PK | 의미 | 방 이동 관점 한계 |
|---|---|---|---|
| `room_category` | `g_idx` | **숙소/그룹**. `g_name`(CAPITAL1, S hotel(H)_M …), `g_type` M/F/C(=FAMILY), `bldg_type` C/E/F/P/S(권역), `g_display` | 성별 규칙이 그룹 단위로만 존재. 방·침대 단위 성별 규칙 없음 |
| `room_info` | `i_idx` | **방**. `i_name`(방번호), `i_limit`(정원), `i_state` Y/N | 정원 1개뿐 — "3인실을 1인실로 운영" 표현 불가 (§6) |
| `room_list` | `r_idx` | **침대**. `i_idx` + `r_num`, `r_state` Y/N | 침대별 잠금/단독사용 개념 없음 |
| `reserve_info` | `ri_idx` | **예약 원장(구간)**. `s_idx, r_idx, s_date, e_date, ri_type` | 날짜가 varchar. 시각(HH:MM) 없음 |
| `room_reserve` | `rr_idx` | **예약 일자 전개**. `r_idx(침대) × rr_date` 하루 1행 + `s_idx, ri_type`(I/S/E) | 배치도의 실질 정본. **미래 날짜 행 보유 가능 → 미래 배정 표현 가능** |
| `room_move` | `m_idx` | **입/퇴실·이동 로그**. `pre_room/next_room`(= `r_idx` 침대), `check_name` S(입실)/E(퇴실)/M(이동), `check_date`, `m_state` | 상태·사유·담당자·시간·취소 없음. 사실상 사후 로그 |
| `room_change_log` | `change_idx` | **룸타입 변경 신청 이력** | `old_room_info`=r_idx, `new_room_cate`=인실 → 의미 불일치(대소비교 불가, data.js 주석에 기록됨) |
| `room_date` | `r_idx` | 방별 날짜 메모 46행 | 사실상 미사용 |
| `student_info` | `s_idx` | `s_gender, s_nation, s_room`(텍스트 현재방), `s_campus`, `s_flight`(픽업일정 자유텍스트), `s_sdate/s_edate`, `now_status` | 졸업일·실제 퇴실일·도착시각이 정형 필드로 없음 (§13 의 근본 원인) |

**중요 발견 — 외부 숙소는 이미 같은 모델 안에 있다.**
`room_category` 의 표시 그룹(`g_display='Y'`) 에 `S hotel(H)_M/_F/_Family`, `Canberry(Cb)_M/_F/_Family`, `Citadines hotel`, `Amethyst(AM)_*`, `CAPITAL(O)`, `ENCANTO(O)` 가 모두 존재한다.
→ **요청서 §8 "외부 숙소 이동"은 새 `Accommodation` 테이블이 아니라 그룹 간 이동으로 구현한다.**
숙소 = `room_category`, 캠퍼스 = `bldg_type`(E=CAPITAL권역, S=ENCANTO권역) + 별도 매핑 테이블로 "외부/내부" 플래그만 추가한다.

### 1.2 신전산 측 이미 존재하는 자산 (재사용)

| 대상 | 위치 | 재사용 포인트 |
|---|---|---|
| `app.room_blocks` + `app.room_block_list/set/release` | `migration/schema/room_blocks.sql` | **이번 설계의 레퍼런스 구현.** 오버레이 원장 + 소프트해제 + 멱등키 + UNIQUE 부분인덱스 + `security definer` RPC + RLS 기본거부 |
| `public.dorm_reservations` (+ `actual_check_in/out`, `early_checkout_days`, `dorm_early_checkouts` 뷰) | `migration/schema/reservations.sql`, `actual_checkout.sql` | **§20-12 "졸업일과 실제 퇴실일이 다르면 실제 퇴실일 우선"이 이미 구현되어 있다.** 계획(check_out) vs 실적(actual_check_out) 이원화 완료 |
| `app.change_log` + write_layer | `migration/schema/change_log.sql`, `write_layer.sql` | 쓰기 화이트리스트·멱등·역방향 동기화 규약 |
| `/api/edit`, `/api/blocks` | `deploy/api/edit.js`, `blocks.js` | 세션검증(Lv8 이상 쓰기) + `idem` 멱등키 + RPC 호출 패턴 그대로 복제 |
| 배치도 렌더 | `deploy/api/data.js` `loadRoomstat()`, `deploy/index.html` (`roomstat` / `spec` 화면) | 그룹>방>침대>구간 세그먼트 구조. **여기에 미래/이동 레이어를 얹는다** |

### 1.3 기존 배정 처리 흐름 (요청서 §21 사전보고 ②)

```
[구전산] 예약 등록 → reserve_info(구간) 생성 → room_reserve(일자 전개) 다건 INSERT
         방 이동     → room_move 로그 1행 + room_reserve 일자행 재작성
         실제 퇴실   → room_reserve 마지막 날짜가 곧 실제 퇴실일

[신전산] GET /api/data?parts=roomstat&month=YYYY-MM
         └ legacy.room_category(g_display=Y) → room_info(i_state=Y) → room_list(r_state=Y)
         └ legacy.room_reserve 를 (r_idx, ri_idx, s_idx) 로 group by → min/max 로 구간 압축
         └ 이름은 student_info 에서 별도 조회 매핑
         └ 중심월 ±6개월 창만 조회
         → { groups:[{ rooms:[{ no, per, gender, beds:[{ segs:[{s,e,nm,si,st,et}] }] }] }] }
```

**현재 프론트에는 침대의 `r_idx` 가 내려가지 않는다** (`beds[].name` 만 존재).
→ 이동 등록 시 대상 침대를 식별할 수 없다. **1차 개발의 선행 과제**로 `r_idx`/`i_idx` 노출이 필요하다.

## 2. 데이터 모델 설계

요청서 §16 의 권장 구조를 그대로 쓰지 않고, **레거시와 충돌하지 않도록 축소·정렬**한다.
(요청서 §21 "기존 모델을 최대한 유지하면서 필요한 마이그레이션을 설계한다" 원칙)

### 2.1 `app.room_assignments` — 배정 오버레이 (요청서 `RoomAssignment`)

레거시 `room_reserve` 를 대체하지 않는다. **레거시에 아직 없는 배정만** 담는 오버레이다.

| 컬럼 | 비고 |
|---|---|
| `id` | bigserial |
| `s_idx` | 학생 (legacy.student_info) |
| `r_idx` | **침대**(legacy.room_list). 방 전체 배정 시에도 침대 단위로 전개 |
| `i_idx`, `g_idx` | 파생(조회 성능·표시용) |
| `assignment_type` | `FUTURE` / `TEMPORARY` / `HOTEL` / `FAMILY` (※ `CURRENT` 는 저장하지 않음 — 아래 참고) |
| `start_at`, `end_at` | **timestamptz**. 시각 포함(요청서 §2.2 09:30) |
| `period` | `daterange` 생성컬럼 — EXCLUDE 제약용 |
| `status` | `DRAFT / PENDING / CONFIRMED / ACTIVE / COMPLETED / CANCELLED` |
| `room_type_at_assignment` | 배정 시점의 인실(스냅샷) |
| `gender_rule` | `M/F/MIXED/FAMILY` |
| `source_move_id` | 어느 이동으로 생겼는가 |
| `created_by/at`, `updated_by/at`, `cancelled_at` | 이력 보존(삭제 금지) |

> **`CURRENT` 를 저장하지 않는 이유.** 현재 배정의 정본은 `legacy.room_reserve` 다. `CURRENT` 행을 별도로 만들면 즉시 이중 정본이 되어 요청서 §12 "한 학생이 같은 날짜에 두 방에 현재 배정됨" 오류를 **우리가 직접 생산**하게 된다.
> 대신 뷰로 정의한다:
> ```
> app.v_assignment_current  := legacy.room_reserve WHERE rr_date = :asof
> app.v_assignment_future   := app.room_assignments WHERE start_at > :asof AND status NOT IN (CANCELLED)
> app.v_bed_state(:asof)    := 두 뷰 + app.room_blocks + app.room_ops 를 합성한 침대 상태
> ```

**DB 레벨 겹침 차단** (요청서 §20-11):
```sql
create extension if not exists btree_gist;
alter table app.room_assignments add constraint ex_assign_overlap
  exclude using gist (r_idx with =, period with &&)
  where (status in ('CONFIRMED','ACTIVE'));
```
※ 레거시 실적과의 겹침은 제약으로 못 잡으므로 **RPC 내부 검증 + 화면 경고**로 이중 방어한다.

### 2.2 `app.room_moves` — 이동 원장 (요청서 §3, `RoomMove`)

`s_idx / from_r_idx / to_r_idx / to_assignment_id / planned_move_at / actual_move_at / move_reason / move_status / priority / depends_on_move_id / vehicle / staff / note / exception_reason / created_by / completed_by / idem_key`

`move_status`: `REVIEW`(검토 필요) → `PLANNED`(이동 예정) → `CONFIRMED`(이동 확정) → `COMPLETED`(이동 완료) / `CANCELLED`(이동 취소) — 요청서 §3 5단계 그대로.

- `depends_on_move_id` → §11 선행/후속 이동. 선행이 `COMPLETED` 아니면 완료 차단.
- `idem_key` UNIQUE → 더블서밋 방지 (메모리 규칙: 저장 idempotency 필수).
- **삭제 없음.** 취소도 `CANCELLED` 상태 + `cancelled_at` (§15).

### 2.3 `app.room_ops` — 운영 정원/단독 사용 (요청서 §6, `RoomOperationSetting`)

`i_idx / default_capacity(=room_info.i_limit 스냅샷) / operating_capacity / operating_room_type / exclusive_use / exclusive_use_start_at / exclusive_use_end_at / additional_assignment_allowed / note`

→ "3인실을 1인실로 판매" 시 나머지 2침대는 배치도에서 **`빈 침대`가 아니라 `운영상 사용 불가`(LOCK, 보라색)** 로 렌더 (§6, §9).
→ 구현상 `app.room_blocks(reason='HOLD')` 를 자동 생성하는 방식과, 별도 테이블로 두는 방식 중 **별도 테이블**을 택한다. 이유: 블록은 "정비/청소로 못 쓰는 방", 운영정원은 "팔지 않기로 한 방"으로 의미가 다르고 해제 주체도 다르다.

### 2.4 `app.cleaning_schedule` — 청소 (요청서 §5.3, `CleaningSchedule`)
`i_idx / r_idx / prev_assignment_ref / next_assignment_ref / cleaning_start_at / cleaning_end_at / status(PENDING/IN_PROGRESS/DONE) / staff`
+ `app.room_settings` 에 전역 `min_cleaning_minutes`(기본 60) — 관리자 설정 가능 (§5.3).

### 2.5 `app.family_groups` / `app.family_members` (요청서 §7)
`family_group_id / label / check_in / check_out / mixed_gender_allowed` + 구성원(`s_idx`, 관계).
가족실 검사: **같은 `family_group_id` 가 아닌** 남/여가 같은 침대·방에서 기간이 겹치면 차단 (§20-7).

### 2.6 `app.room_move_events` — 감사 로그
이동 원장의 모든 상태 전이를 append-only 로 기록 (변경 전/후 숙소·방·침대, 처리자, 시각, 예외 승인 사유). §15 요구사항 전량 충족.

## 3. 검증 엔진 설계 (요청서 §5, §14)

단일 진입점 RPC: **`app.room_move_validate(p_s_idx, p_to_r_idx, p_planned_at, p_options) → jsonb`**
반환: `{ ok, blocks:[...], warnings:[...], info:{...} }`

| # | 검사 | 결과 | 근거 데이터 |
|---|---|---|---|
| V1 | 기존 입실자 잔류 | **BLOCK** | `room_reserve` 마지막 날짜 vs `dorm_reservations.actual_check_out`(실적 우선, §20-12) |
| V2 | 미래 배정 겹침 | **BLOCK** | `app.room_assignments` EXCLUDE 제약 + 사전 조회 |
| V3 | 신규 입실 예정자 충돌 | **BLOCK/WARN** | 대상 침대의 미래 예약 + `student_info.s_flight`(도착/픽업) |
| V4 | 성별 규칙 | **BLOCK** | `room_category.g_type` + 동일 방 재실자 성별. FAMILY 그룹은 §2.5 규칙으로 |
| V5 | 운영상 잠금/단독사용 | **BLOCK** | `app.room_ops`, `app.room_blocks` |
| V6 | 청소 시간 부족 | **WARN(예외 가능)** | 이전 퇴실시각 + `min_cleaning_minutes` |
| V7 | 룸타입 불일치 | **WARN(예외 가능)** | 신청 인실 vs `room_info.i_limit`/`operating_room_type` |
| V8 | 정보 미확인 | **WARN → 확정 차단** | 퇴실일·도착시각·성별·룸타입 결측 시 §13 "정보 확인 필요" 목록 반환 |
| V9 | 선행 이동 미완료 | **BLOCK(완료 시점)** | `depends_on_move_id` |
| V10 | 학생 미래배정 중복 | **WARN** | 같은 `s_idx` 의 미완료 이동/미래배정 2건 이상 |

**WARN 을 넘길 때는 `exception_reason` + 담당자 기록을 강제**한다 (§14, §5.5).

## 4. API 설계 (요청서 §17)

PHP 없음. Vercel 서버리스 + Postgres 직결 (기존 `deploy/api/*.js` 규약 동일: 세션 필수, 쓰기 Lv8+, `idem` 멱등키, RPC 내부 재검증).

| 메서드 | 경로 | RPC | 비고 |
|---|---|---|---|
| GET | `/api/moves?from=&to=&status=` | `app.room_move_list` | 이동 목록/보드 |
| GET | `/api/moves?op=validate&...` | `app.room_move_validate` | 폼 입력 중 실시간 검사 |
| GET | `/api/moves?op=timeline&r_idx=` | `app.bed_timeline` | §10 침대 타임라인 |
| POST | `/api/moves {op:'create'}` | `app.room_move_create` | 검증 → 미래 배정 생성 → 이동 등록 (**1 트랜잭션**) |
| POST | `/api/moves {op:'complete'}` | `app.room_move_complete` | 상태 재확인 → 기존 배정 종료 → 미래→현재 전환 → 실제시각/담당자 기록 → 이력 (**1 트랜잭션, 실패 시 전량 롤백**, §20-13) |
| POST | `/api/moves {op:'cancel'}` | `app.room_move_cancel` | 미래 배정만 CANCELLED. 현재 배정 무변경 (§20-5) |
| GET | `/api/data?parts=roomstat` (확장) | — | 침대 `r_idx` 노출 + 미래/이동/청소/락 레이어 동봉 |
| GET | `/api/moves?op=cleanup` | `app.room_data_issues` | §12 "방 배정 데이터 정리 필요" 목록 (읽기 전용, 자동 삭제 없음) |

> **PL/pgSQL 함수 1개 = 1 트랜잭션**이므로 §4 이동 완료의 원자성은 함수 경계로 보장된다. 별도 트랜잭션 제어 코드 불필요.
> 완료 처리는 `app.change_log` 에 기록 → 구전산 역방향 일일 동기화가 집어간다 (기존 규약).

## 5. 화면 설계 (요청서 §9, §10, §11)

### 5.1 배치도(DORM STATUS) 셀 확장
색 + **아이콘 + 텍스트** 병기 (색맹 대응, §9):

| 상태 | 색 | 배지 |
|---|---|---|
| 현재 비어 있음 | 회색 | — |
| 현재 입실 중 | 파랑 | 이름 |
| 이동/입실 예정 | 초록 | **`→IN`** / **`↔MOVE`** |

셀 툴팁: 현재 학생·기간 / 미래 학생·기간 / 이동 예정시각 / 성별 / 룸타입 / 청소 상태.
→ 요청서 §9 "초록 하나로 들어올 학생과 나갈 학생을 모두 표현하지 않는다" 반영: **IN/OUT 배지로 분리**.

### 5.2 신규 화면
- **ROOM MOVES (이동 보드)** — 상태별 칸반/목록, 날짜 필터, 우선순위 드래그(§11), 일괄 완료.

### ✅ 결정 1 — 정보 미확인 판정: **신전산 전용 입력 필드를 만든다**

**값 우선순위(읽기 규칙):** `app.student_stay_facts` → `public.dorm_reservations`(실적) → `legacy.student_info`(계획).
**판정:** 이동 확정(`CONFIRMED`)에 필요한 항목이 비어 있으면 상태를 `REVIEW`(정보 확인 필요)로 잠그고, **구체적으로 어떤 칸이 비었는지** 목록으로 반환한다. `PLANNED` 까지는 등록 가능하되 `CONFIRMED`/`COMPLETED` 는 차단.
**입력 UI:** 이동 등록 모달 안에서 결측 칸을 바로 채울 수 있게 한다(별도 화면 왕복 없이). 학생 상세 모달에도 같은 칸 노출.

### ✅ 결정 3 — 전환 기간: **신전산 단독 운영**

방 이동 관리는 신전산에서만 한다. 구전산 방 이동 화면은 사용하지 않는다.
→ 이중 입력 충돌 규칙이 불필요해지고, `app.room_moves` 가 **이동의 유일한 정본**이 된다.
→ 다만 다음 두 가지는 반드시 지킨다:
- 구전산 배치도는 일일 역동기화 시점까지 이전 상태를 보여준다 → **구전산 배치도를 이동 판단 근거로 쓰지 말 것**을 운영 규칙으로 공지.
- 구전산에서 방 이동이 발생하면(예약 담당자가 실수로 입력) 신전산이 감지해 §12 "정리 필요" 목록에 올린다(외부 변경 탐지). 자동 반영·자동 삭제는 하지 않는다.

### ✅ 결정 4 — 최소 청소 시간: **기본 60분, 변경 가능**

`app.room_settings` 키-값 테이블에 `min_cleaning_minutes = 60` 을 시드하고 **관리자 화면에서 수정 가능**하게 한다.
확장 여지를 위해 조회는 **가장 구체적인 값 우선**으로 해석한다:
`방(i_idx)별 설정` → `그룹(g_idx)별 설정` → `전역 기본값(60)`
1차 개발에서는 전역값만 UI로 노출하고, 그룹/방별 오버라이드는 스키마만 준비해 둔다(2차에서 필요 시 화면 추가).

### ✅ 결정 5 — 예외 승인: **상위 레벨(Lv10+)만 승인**

이동 등록·완료는 현행 쓰기 권한(Lv8+)이 그대로 하되, **예외가 걸린 이동의 확정은 Lv10+ 만 가능**하다.

**요청서 §3 의 5단계 상태는 그대로 두고**, 승인은 별도 필드로 표현한다(상태를 6개로 늘리면 기존 요구사항과 어긋난다).

| `app.room_moves` 추가 필드 | 의미 |
|---|---|
| `exception_flags jsonb` | 어떤 WARN 을 넘기려는가 — `["ROOM_TYPE_MISMATCH","CLEANING_SHORT"]` |
| `exception_reason` | 담당자가 적는 사유 (필수) |
| `exception_approved_by` / `exception_approved_at` | Lv10+ 승인자·시각 |

**동작 규칙**
- Lv8 담당자: WARN 이 있어도 `PLANNED`(이동 예정)까지 저장 가능. `exception_flags` + `exception_reason` 을 함께 기록.
- `CONFIRMED`(이동 확정) 전이: `exception_flags` 가 비어 있으면 Lv8+ 가능. **비어 있지 않으면 `exception_approved_at` 이 채워져야만 가능** → 즉 Lv10+ 승인 필수.
- `COMPLETED`(이동 완료): 승인되지 않은 예외가 남아 있으면 차단.
- 화면 파생 배지 **`승인 대기`** = `exception_flags ≠ [] AND exception_approved_at IS NULL`. 이동 보드에 별도 필터로 노출.
- 승인/반려 모두 `app.room_move_events` 에 append (반려 시 사유 필수).
- **BLOCK 항목은 Lv10 도 넘길 수 없다** — DB 제약과 RPC 가 거부한다.

**추가 API**
| 메서드 | 경로 | 비고 |
|---|---|---|
| POST | `/api/moves {op:'approve', move_id, note}` | Lv10+ 전용 |
| POST | `/api/moves {op:'reject', move_id, reason}` | Lv10+ 전용, 사유 필수 |

**운영 리스크와 완화:** 승인자 부재 시 이동이 지연된다(예: 주말 새벽 도착 건). 완화책 — 이동 보드에 `승인 대기` 를 최상단 고정 + 건수 배지, 2차에서 알림 연동. 다만 **예정(PLANNED) 등록과 실무 준비는 승인 없이도 진행**되므로 작업 자체는 막히지 않는다.

## 13. "예외 승인" 의 정의 (결정 5의 대상 범위)

요청서 §14 는 경고를 **차단(BLOCK)** 과 **확인 후 예외 처리 가능(WARN)** 으로 나눈다.
**예외 승인 = WARN 을 무릅쓰고 이동을 확정하는 행위**이며, 사유·승인자·시각을 남긴다. **승인 주체는 Lv10+**(결정 5).

### 절대 넘길 수 없는 것 (BLOCK — 승인해도 불가)
- 같은 침대에 일정이 겹침 (DB EXCLUDE 제약이 물리적으로 거부)
- 기존 학생이 아직 퇴실하지 않음
- 남녀 배정 규칙 위반
- 운영상 잠긴 침대 / 단독 사용 방의 추가 배정
- 선행 이동 미완료 상태에서 후속 이동 완료

### 승인으로 넘길 수 있는 것 (WARN — 이것이 "예외 승인" 대상)
| 상황 | 실제 업무 예시 |
|---|---|
| 신청 룸타입 ≠ 실제 룸타입 | 3인실 신청인데 2인실 배정 |
| 청소 시간이 최소값(60분) 미만 | 13:00 퇴실 → 13:30 입실 |
| 입실/퇴실 시각 미입력 | 날짜만 알고 시각 미정 |
| 외부 숙소 이동 시각 미정 | S Hotel 픽업 시간 미확정 |
| 가족실 관계 정보 없음 | 가족 구성원 연결 미등록 |
| 같은 학생 미래 배정 중복 | 이동을 두 번 등록 |

승인 시 `app.room_moves.exception_reason` + 승인자 + 시각이 `app.room_move_events` 에 남고, 배치도 셀과 이동 목록에 **예외 배지**가 표시된다.

**결정 필요:** 이 승인을 ⑴ 이동 등록 권한자(현행 Lv8+)가 그대로 할 것인가, ⑵ 상위 레벨(예: Lv10 / 기숙사 책임자)만 할 수 있게 분리할 것인가.
