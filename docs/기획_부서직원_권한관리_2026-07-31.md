# 기획서 — 부서·직원별 레벨/권한 관리 섹션

> 작성 2026-07-31 · **기획만(코딩 미실시)** · 대상: 신전산(smeag-bay) 관리자
> 관련: `deploy/api/data.js`(PART_ACCESS·STAFF_LEVEL) · `deploy/api/edit.js`(WRITE_MIN_LEVEL) · `deploy/index.html`(DEPTS·PERMS·R.perms) · `migration/schema/member_level_override.sql`

## 1. 왜 필요한가 (현행 실측 문제)

지금 권한이 **세 군데에서 따로 놀고 있고, 그중 하나는 보안 효과가 전혀 없습니다.**

| # | 현행 장치 | 위치 | 저장소 | 실제 효과 |
|---|---|---|---|---|
| ① | `mb_level` (Lv1~10) | `cms.g4_member` (레거시 미러) | 레거시 원본 | 서버 인가의 **유일한 실효 기준** |
| ② | 조각별 접근등급 `PART_ACCESS` (internal/business/master) + `STAFF_LEVEL=8`, `WRITE_MIN_LEVEL=8` | `/api/data`, `/api/edit` | 코드 상수 | 실효(서버 차단). 단 **전 직원 일괄 기준**이라 부서 구분 없음 |
| ③ | 부서 RBAC `DEPTS`/`PERMS`/`deptAllows()` | `deploy/index.html` | **브라우저 localStorage** | ⚠ **보안 효과 0** — 사용자가 콘솔·DevTools로 바꾸면 그대로 뚫림. 서버는 이 값을 모름 |

추가로 오늘 확인된 사실:

- 레거시 실무자 **대부분이 Lv7**(Lv10 5명 · Lv9 1 · Lv8 1 · **Lv7 24명** · Lv6 1 · Lv5 이하 2,000+).
- `STAFF_LEVEL=8` 기준이라 **Lv7 24명 전원이 403**. 오늘 kenneth 1명만 `app.member_level_override` 로 Lv10 부여해 임시 해소.
- 즉 현재 운영 상태는 **"전부 막힘 아니면 전부 열림"** 의 이분법이며, 부서별 최소권한 원칙이 서버에 존재하지 않음.

**목표**: 부서·직원 단위로 **서버에서 강제되는** 권한을 관리자가 화면에서 직접 부여/회수하고, 그 이력이 남게 한다.

## 1-2. 레거시는 어떻게 되어 있나 (2026-07-31 DB 실측)

**결론: 레거시에는 부서·직원별 권한 체계가 사실상 없습니다. `mb_level` 숫자 하나로 관리자/유학원/일반을 가르는 단일 게이트뿐입니다.**

### 레거시 권한 구조 요약

```
Lv10  최고관리자(cf_admin=cebusme2) + Joon·katie·cebusme·cebusme00  … 전권
Lv9   cebusme1(Rachel Jung)                                        … 전권에 준함
Lv8   fumi                                                          … 관리자
Lv7   실무자 24명 (kenneth 포함)                                     … 관리자 화면 전부 접근
Lv6   jeff (게시판 열람 하한선)
Lv5   1,583  유학원 계정(mb_10=유학원코드) → agency_page.php 포털
Lv3   287    유학원 하위/미확정
Lv1   150    일반 회원
```

- **관리 화면(`/gnuboard4/adm/*.php`) 자체가 레벨 검사만** 합니다. 그래서 기숙사 담당도 재무 화면을, 프론트도 회원 PII를 볼 수 있습니다.
- **부서 개념이 DB에 없습니다.** `g4_member` 에 부서 컬럼이 없고(mb_1~mb_11은 유학원 표기명·유학원코드·계약일·비중 등 유학원용), 부서를 담는 별도 테이블도 덤프 55개 중 없습니다.
- **직원 계정 구분은 계정명 관례로만** 존재합니다 — `encanto1`·`encantoadmin1/2`·`capital1`(캠퍼스), `kitchenmanager`(급식), `recordingofficer`(기록), `judedesigner`(디자인), `supervisor`. 즉 **조직 정보가 문자열 관습에 숨어 있는 상태**입니다.
- 퇴사·차단은 `mb_leave_date`·`mb_intercept_date`·`mb_memo_call='block'` 으로만 표기됩니다(권한 회수 절차 없음).

### 이 사실이 기획에 주는 의미

1. **"레거시대로 재현"할 권한 체계가 애초에 없습니다.** 메뉴·화면은 레거시를 그대로 따라가되, 권한만은 **신전산에서 새로 설계**하는 것이 맞습니다(§3).
2. 신전산이 `STAFF_LEVEL=8` 을 쓴 것이 오히려 레거시보다 엄격해 **Lv7 24명이 전부 막혔던 것**이 오늘 사고의 원인이었습니다. 레거시 기준선은 **Lv7**입니다.
3. 따라서 이행 1단계는 **"레거시와 동등(Lv7=관리자 전권)"으로 먼저 맞춰 업무를 정상화**하고, 그 다음 부서별 최소권한으로 **좁혀 가는** 순서가 안전합니다. 처음부터 조이면 현업이 멈춥니다.
4. 부서 배정 초안은 **계정명 관례 + 활동 이력**(방변경 로그 작성자·게시글 작성자·최근 접속)으로 자동 제안하고 관리자가 검수하는 방식이 현실적입니다 — 레거시에서 가져올 부서 데이터가 없기 때문입니다.

## 2. 범위

**포함(In)**
- 부서 마스터 관리(생성·수정·비활성)
- 부서별 권한 프로필(메뉴 카테고리 + 데이터 조각 + 읽기/쓰기)
- 직원 계정의 부서 배정(다중 부서 허용)
- 계정별 예외 권한(추가 허용 / 개별 차단) 및 유효권한 시뮬레이션
- 서버측 강제(`/api/auth`·`/api/data`·`/api/edit`) 및 감사로그
- 레거시 `mb_level` 을 건드리지 않는 오버라이드 구조

**제외(Out)**
- 레거시 `cms.g4_member.mb_level` 원본 수정 — **불가침**(다음 동기화 원복 + 역방향 동기화 위험)
- 유학원(외부) 계정 권한 — 기존 `scope.agency` 로직 유지, 이번 섹션은 **내부 직원 전용**
- 비밀번호 정책·2FA(별도 과제)

## 3. 권한 모델 설계

### 3-1. 3계층 + 예외

```
 계정(mb_id)
   └─ 부서 배정 (N:M, 주부서 1개 지정)
        └─ 부서 권한 프로필
             ├─ 메뉴 카테고리 접근  (setting/member/board/agency/record/student/dorm/financial/cash)
             ├─ 데이터 조각 접근    (students, roomstat, pickup, deposits, chgref, members, commission, changelog, boards, dayoff, elec, courses, tuition, farmgym, agencyvisit, points, visits …)
             └─ 쓰기 권한           (조각별 read / write)
   └─ 계정 예외        (+추가 허용 / −개별 차단, 사유·만료일 필수)
   └─ 레벨 오버라이드  (기존 app.member_level_override — 하위호환용, 신규 부여는 지양)
```

### 3-2. 유효권한 산출 규칙 (서버 단일 함수)

```
효과권한(계정, 조각, 동작) =
    ① 계정 차단(−) 이 있으면            → 거부 (최우선)
    ② 계정 추가허용(+) 이 있으면        → 허용
    ③ 배정된 부서들의 권한 합집합(OR)   → 허용/거부
    ④ 아무 부서도 없으면                → 레벨 폴백: max(mb_level, level_override) ≥ STAFF_LEVEL
```

- **차단(−) 이 허용(+) 보다 강함**(deny-overrides). 사고 시 즉시 봉쇄 가능.
- ④ 폴백을 두는 이유: 이행기간에 부서 미배정 계정이 갑자기 잠기는 사고 방지. **이행 완료 후 폴백 제거**가 최종 목표.
- 유학원 계정은 이 경로를 타지 않고 기존 `scope.agency` 규칙 유지.

### 3-3. 기본 제공 부서 프로필(초안 — 확정 필요)

| 부서 | 메뉴 카테고리 | 데이터 조각 | 쓰기 |
|---|---|---|---|
| **원장/대표** | 전체 | 전체 | 전체 |
| **학생관리부** | Record·Student's·Board | students, chgref, deposits, farmgym, boards | students(수정/변경/연장), chgref |
| **기숙사부** | Record·Dormitory·Student's(읽기) | roomstat, pickup, changelog, students(읽기), boards | 방배정·방변경·방막기 |
| **재무부** | Record·Financial·Cash Cards·Student's(읽기) | students(읽기), deposits, chgref, commission, courses, tuition | 인보이스 발행, 센터수납, 수금 |
| **유학원관리부** | Record·Agency·Student's(읽기) | commission, students(읽기), agencyvisit | 커미션 규칙 |
| **프론트/기타** | Record·Student's(읽기)·Dormitory(읽기) | students(읽기), roomstat(읽기), pickup | 없음 |
| **시스템관리** | 전체 + Setting | 전체 + changelog·members | 전체 + 권한관리 |

> ⚠ `members`(회원 PII)·`changelog`(감사로그)·`commission`(수수료) 는 **기본적으로 원장·재무·시스템관리만**. 부서 프로필에서 체크만으로 열리지 않게 "민감 조각"으로 별도 표시.

## 4. 데이터 모델 (app 스키마 — 레거시 무변경)

| 테이블 | 컬럼(요지) | 비고 |
|---|---|---|
| `app.dept` | dept_id(PK) · name · name_en · active · sort · memo | 부서 마스터 |
| `app.dept_perm` | dept_id · scope_type(`cat`\|`part`) · scope_key · can_read · can_write | 부서 권한 프로필(행 단위) |
| `app.member_dept` | mb_id · dept_id · is_primary · assigned_by · assigned_at | 계정↔부서 N:M |
| `app.member_perm_override` | mb_id · scope_type · scope_key · effect(`allow`\|`deny`) · can_write · reason(필수) · expires_at · updated_by | 계정 예외 |
| `app.member_level_override` | (기존) mb_id · mb_level · active · memo | 오늘 신설분. 하위호환 유지, 신규는 지양 |
| `app.perm_audit` | ts · actor · action · target_mb_id/dept_id · before(jsonb) · after(jsonb) · ip | **권한 변경 전량 기록** |

- 조회 헬퍼: `app.effective_perm(mb_id)` → `{cats[], parts[{key,read,write}], source}` 를 jsonb 로 반환(서버 1회 호출·요청당 캐시).
- 성능: 계정당 수십 행 규모 → 인덱스는 PK 로 충분. `/api/data` 는 요청당 1회 조회 후 메모리 캐시(현재 `member_level_of` 와 동일 패턴).

## 5. 서버 적용 지점

| 위치 | 변경 요지 |
|---|---|
| `/api/auth` (로그인) | 세션 JWT 에 `dept:[...]`, `perm_ver`(권한 버전 해시) 추가. 레벨은 기존대로 max(레거시, 오버라이드) |

## 6. 화면 기획 — `Record ▸ 권한설정` 확장

기존 권한설정 화면을 **3탭**으로 확장.

### 탭 A. 부서 (Departments)
```
┌ 부서 목록 ─────────────┐ ┌ 권한 프로필: 학생관리부 ────────────────────┐
│ ● 원장/대표      (3명) │ │ 메뉴 카테고리                                │
│ ● 학생관리부     (9명) │ │  ☑Record ☑Student's ☑Board ☐Dormitory …    │
│ ● 기숙사부       (6명) │ │ 데이터 조각            읽기  쓰기            │
│ ● 재무부         (4명) │ │  students             ☑     ☑              │
│ ● 유학원관리부   (2명) │ │  chgref               ☑     ☑              │
│ ● 프론트         (1명) │ │  members  ⚠민감       ☐     ☐              │
│ + 부서 추가            │ │  changelog ⚠민감      ☐     ☐              │
└────────────────────────┘ │ [저장]  변경 3건 미리보기 →                  │
                           └──────────────────────────────────────────────┘
```
- 민감 조각(members·changelog·commission)은 ⚠ 배지 + 체크 시 **2차 확인 모달**.
- 저장 전 **변경 미리보기**(무엇이 열리고 닫히는지, 영향 인원 N명) 필수.

### 탭 B. 직원 (Members)
- 목록: 계정ID · 이름 · 레거시 Lv · **부서(주/부)** · 유효권한 요약 · 최근접속 · 상태
- 필터: 부서 / 레벨 / 미배정만 / 예외 있는 계정만 / 검색
- 다중 선택 → **부서 일괄 배정**(24명 이행에 필수)
- 행 클릭 → 상세 패널
  - 부서 배정(주부서 지정)
  - **계정 예외**: `+추가 허용` / `−차단`, **사유·만료일 필수**
  - **유효권한 시뮬레이터**: "이 계정으로 STUDENT LIST 를 열면? → 허용(학생관리부 경유)" 처럼 **판정 경로를 문장으로** 표시
  - 레거시 Lv 는 읽기전용 표시(수정 불가 — 원본 불가침 명시)

### 탭 C. 이력 (Audit)
- 언제·누가·누구의 무엇을 바꿨는지(before→after diff), 필터·엑셀.
- 권한 변경은 **되돌리기(Revert)** 버튼 제공(감사로그 기반).

### 안전장치
1. **자기 권한 강등 금지** — 본인 계정의 시스템관리 권한 회수 불가.
2. **최소 1명 보장** — 시스템관리 권한자가 0명이 되는 저장 차단.
3. **위험 변경 2차 확인** — 민감 조각 개방, 부서 삭제, 10명 이상 일괄 변경.
4. **만료일 있는 예외** — 임시 권한은 자동 소멸(만료 임박 7일 전 대시보드 알림).
5. 모든 변경 **감사 기록 + 멱등키**(더블서밋 방지 원칙 준수).

## 7. 이행 계획 (현행 → 신규)

| 단계 | 내용 | 리스크 |
|---|---|---|
| 0 | 스키마 생성 + 기본 부서 7종 시드. **적용만 하고 강제는 꺼둠**(shadow mode) | 없음(읽기만) |

| 2 | shadow mode 로 1주 관찰: "신규 규칙이었다면 거부됐을 요청" 을 로그로만 수집 | 실차단 없음 |

## 9. 확정이 필요한 사항 (기획 승인 시 함께 결정)

1. **부서 목록 확정** — 위 7종(원장/학생관리/기숙사/재무/유학원관리/프론트/시스템관리)으로 갈지, 실제 조직도 기준으로 바꿀지. 실제 부서명·인원을 주시면 그대로 반영.
2. **민감 조각 범위** — `members`(회원 PII)·`changelog`(552K 감사로그)·`commission`(수수료)을 원장·재무·시스템관리로 제한하는 안에 동의하시는지.
3. **쓰기 권한 단위** — 조각 단위(students 쓰기)로 충분한지, 아니면 행위 단위(방배정/인보이스발행/센터수납 각각)로 더 잘게 나눌지. **행위 단위 권장**(인보이스 발행은 재무만).
4. **이행기 폴백 유지 기간** — 3단계에서 몇 주 유지할지.
5. **누가 권한관리자인가** — 시스템관리 권한을 가질 계정 지정(최소 2명 권장: 1명은 백업).
6. 오늘 임시 부여한 **kenneth Lv10 오버라이드**를 이 체계로 흡수할지(권장) 유지할지.
